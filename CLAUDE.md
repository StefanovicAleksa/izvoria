# CLAUDE.md

Guidance for Claude Code (and any engineer) working in this repository. Read this before touching `app/`.

## What Izvoria is

Izvoria is a fully **on-premise AI appliance** sold to law firms, hospitals, and other businesses that cannot let their data touch a third-party cloud. A client buys the appliance, points it at their local media/documents, and it:

1. Ingests that data through a local pipeline (transcription, diarization, visual analysis, correction).
2. Indexes it into a local RAG store (PostgreSQL + pgvector, hybrid dense + sparse search).
3. Lets people ask questions of a local LLM that answers **only** from that indexed data, with a citation back to the source chunk for every claim it makes.

The non-negotiable product requirement: **the model must never recall or state something that isn't grounded in the client's ingested data, and every answer must be traceable to a source.** A lawyer or doctor relying on a hallucinated answer is the failure mode this whole architecture exists to prevent. This is why the pipeline has multiple explicit correction/scrubbing stages (hallucination correction, retrieval hallucination scrubbing, visual hallucination correction) rather than trusting any single model pass.

No data leaves the premises — there is no cloud API call anywhere in the inference path. It's sold as appliance hardware, not a hosted SaaS product.

## Hardware reality — this drives the whole architecture

- **Dev machine (current):** 1× NVIDIA RTX 3060, **12GB VRAM**, AMD Ryzen 7 2700X, 32GB RAM @ 3200MHz.
- **Target client hardware:** 2× NVIDIA RTX 3060, **24GB VRAM total**, intended to be split so one GPU serves the **ingestion pipeline** and the other serves the **LLM** continuously for live chat.

Because no single GPU here can hold more than one or two of this pipeline's models at once, **nothing in this codebase may assume a model stays resident in VRAM.** Every GPU-bound component loads its model just-in-time, uses it, and releases it. This is not an optimization to add later — it is the baseline design constraint for every feature that touches the GPU. See "Model management rules" below.

The flip side: today the codebase also does not have any concept of *which* GPU a model runs on — there is no `device_id` or `CUDA_VISIBLE_DEVICES` anywhere in `app/core/model_manager/` or `app/core/config.py`. Everything assumes one shared VRAM pool on one device, which matches the dev box but not the target 2-GPU appliance. **Do not silently bake in single-GPU assumptions in new code** (e.g. don't hardcode `cuda:0`) — but also don't try to build out the full dual-GPU pool abstraction speculatively unless a task specifically asks for it. Flag it when it becomes relevant.

## Architecture: feature-first, hexagonal per feature

Every feature — under `app/core/`, `app/features/`, `app/legacy_features/`, and `app/tools/` — follows the **same internal folder convention**, ports-and-adapters style:

```
<feature>/
├── __init__.py
├── domain/          # entities.py, interfaces.py (ports/ABCs), enums.py — pure, no I/O, no framework imports
├── data/             # adapters implementing domain interfaces: model adapters, DB repositories
├── service/          # the feature's public API (e.g. retrieval_api.py) — the ONLY entrypoint other code should call
├── exceptions/        # base.py + specific typed exception modules (database.py, model.py, vram.py, network.py, ...)
└── utils/             # feature-local helpers, almost always including error_mapper.py
```

- `domain/interfaces.py` defines the contracts (e.g. `ITranscriptionAdapter`, `IRetrievalRepository`, `IModelLoader`) — these are what make features swappable and testable in isolation.
- `data/` implements those interfaces against real infrastructure (a specific model library, a specific Postgres table).
- `service/*_api.py` is what everything outside the feature is allowed to call. Never reach into another feature's `data/` directly.
- `exceptions/` + `utils/error_mapper.py`: every feature translates low-level/third-party exceptions (DB errors, CUDA OOM, file-not-found) into its own typed exception hierarchy at the boundary, so callers up the stack only ever see feature-level exceptions.
- Simple features with no persistence or model adapter (e.g. `hallucination_correction`, `scanner`) legitimately omit `data/`. Don't add an empty `data/` folder just for consistency — only add it if there's a real adapter to put there.

### Composition layers above individual features

- **`app/orchestration/service/phases/`** — one `Phase` class per pipeline stage. A Phase wraps a feature's `service` API with job tracking (`JobManager.run_job`) and, for GPU-bound stages, model preload/unload calls around the feature's work.
- **`app/orchestration/service/pipelines/`** — chains Phases into full workflows: `BatchMediaPipeline` / `BatchAudioPipeline` (ingestion), `LiveRetrievalPipeline` / `LiveVerifiedRetrievalPipeline` / `LiveQAPipeline` / `LiveReasoningPipeline` (query-time), and `DeepResearchReportPipeline` (a whole multi-page report per run).
- **`app/engine/`** — the composition root. `IzvoriaBootstrapper.build()` (`service/bootstrap.py`) is the DI container that wires every adapter/API/Phase/Pipeline together and constructs the single shared `ModelManagerOrchestrator`. `IzvoriaEngine` (`service/izvoria_engine.py`) is the top-level facade: `start()/stop()`, `ingest_videos()/ingest_audios()`, `search_standard()/search_verified()/chat()/chat_reasoned()`, and `propose_research_plan()/execute_research_report()`. It holds an `EngineState` lock that makes batch ingestion, report runs and live search/chat **mutually exclusive** — ingestion takes `INGESTING` and a report takes `RESEARCHING`, and either rejects live calls with `EngineBusyError` until it's done. This exists because ingestion and inference currently compete for the same single GPU; splitting them across the two target GPUs is the natural way to lift this restriction, but that work hasn't been done yet.

### How to add a new feature

1. Define the domain interface(s) in `domain/interfaces.py` first — decide the contract before the implementation.
2. Implement the adapter(s) in `data/` against that interface (model wrapper, DB repository). If the feature loads a model, the adapter implements `IModelLoader`.
3. Add a typed exception module under `exceptions/` and wire translation logic into `utils/error_mapper.py`.
4. Expose a `service/<name>_api.py` — this is the only thing other code (a Phase, or another feature) should import.
5. If the feature loads a model: add its path + `_VRAM_REQUIREMENT_MB` to `app/core/config.py` (`Settings`), following the existing naming pattern (`<FEATURE>_MODEL_PATH` / `<FEATURE>_VRAM_REQUIREMENT_MB`).
6. Register the feature's adapters/APIs in `IzvoriaBootstrapper.build()`.
7. If it belongs in a pipeline: add an orchestration `Phase` (`app/orchestration/service/phases/`) and register it in the relevant `Pipeline` (`app/orchestration/service/pipelines/`).
8. Add a unit test directory mirroring the new feature under `tests/features/<name>/...` (see Testing below) — don't skip this even for a first pass; an empty/stubbed test file is better than a missing directory, since the test tree's shape is expected to mirror `app/` exactly.

Use the **`scaffold-izvoria-feature`** skill (`.claude/skills/scaffold-izvoria-feature/`) to generate steps 1–4 and the checklist for 5–8 automatically — it seeds files from `app/features/hallucination_correction` (no-adapter template) or `app/features/rag_retrieval` (model/DB-adapter template) depending on the feature's shape.

## Model management rules

All GPU/VRAM-consuming code must go through `app/core/model_manager/`:

- Every model adapter implements `IModelLoader` (`load(manifest)` / `unload()`).
- Acquire and release models only via `ModelManagerOrchestrator.acquire_model(manifest, loader)` / `release_model(loaded_model, loader)`. Never hold a raw model reference across a call boundary outside that lifecycle — if the orchestrator doesn't know a model is loaded, it can't budget for it or evict it.
- **Warm pool, budgeted by measured footprint.** A model is ACTIVE while held. When a holder releases a type in `MODEL_KEEP_WARM_TYPES` (embedder, reranker, `QA_GENERATION`, `REPORT_AUTHORING`), it goes IDLE: it stays in VRAM, is handed out again for free, and is evicted only when a later load needs the room: the IDLE set that frees the fewest megabytes while making it, least recently used on a tie. Any other type unloads on release.
  - A waiting acquire (`wait_for_clear=True`: live APIs and every preload) never evicts an ACTIVE model. It loads beside the held models when it fits, and otherwise waits for them.
  - A batch acquire (`wait_for_clear=False`: ingestion) evicts everything, as the old single-slot pool did.
  - The budget is the VRAM a load actually took (measured per process), falling back to `max(on-disk size, <FEATURE>_VRAM_REQUIREMENT_MB)`.
  - `MODEL_KEEP_WARM=False` restores the single slot. On the 12 GB card, embedder + reranker + Qwen3.5-9B@128K fit together; the scrubber does not, so it loads only when a chunk is below the rerank trust score.
  - Don't add a type to the warm set without checking that the set still fits the card.
- **Preload-ahead**: Phases that know they'll need a model soon can call `AsyncModelService.trigger_preload()` to start loading it on a background thread (`BackgroundModelWorker`, a 1-worker `ThreadPoolExecutor`) while other I/O-bound work continues, then `resolve_preload()` to block on it when actually needed. `trigger_unload()` is deliberately synchronous (bypasses the worker pool) so it can't deadlock behind a parked preload task.
- Admission control (`OutOfVramError`) budgets, on an empty GPU, **on-disk weight size + learned "backpack" + 500 MB** (beside other residents: measured footprint + the largest backpack among them + 500 MB). The backpack (peak activation/overhead memory beyond the weights, per model path) is learned by a telemetry thread and kept in memory only, so it starts at 0 on every process start. `<FEATURE>_VRAM_REQUIREMENT_MB` is only used when the weights path doesn't exist — still set it, conservatively.
- Always release what you acquire, in a `finally` block, so a failure mid-feature doesn't leak VRAM for the rest of the process.
- **`acquire_model` hands out a shared instance, not a refcounted handle** — `release_model` ends the holding on the first call no matter how many callers hold it (frees it, or for a keep-warm type makes it IDLE and so evictable). That is deliberate (`release_after=False` makes acquires outnumber releases by design), so any release made *on behalf of* someone else must go through `release_preload`, which checks under the orchestrator's lock whether anyone has taken the model since. Freeing one that is in use aborts the process inside llama.cpp's `free_model` rather than raising.
- **Pinned and external types (hosted only, both empty on the appliance).** `MODEL_PINNED_TYPES` are loaded once (`ModelKit.warm_up`) and never released, evicted or unloaded; `MODEL_EXTERNAL_TYPES` are served by a local `llama-server` (`LLM_BACKEND=llama_server`, `LlamaServerChatModel` behind `build_llama`/`chat_completion`) and never budgeted. With `ENGINE_CONCURRENT_LIVE` the orchestrator is `strict_resident`: acquiring any other type raises `ResidencyError`, because concurrent requests sharing a model `release_model` can free is the use-after-free above. This, not a refcount, is what makes the hosted API's concurrency safe; see `docs/web_deploy.md`.
- Before writing or changing code that loads a model, follow the **`izvoria-model-lifecycle`** skill (`.claude/skills/izvoria-model-lifecycle/SKILL.md`): adapter, feature API, Phase and pipeline patterns, preload/discard, and how to test them.

## Languages

An appliance serves every language that has a pack in `data/languages/<code>.toml` (`en`, `sr`), all in one database. **Slovenian is a legacy language**: its pack is kept in `data/languages/legacy/` but not served (weak Whisper accuracy, and the reranker scores Slovenian questions about English material near zero). Only `data/languages/*.toml` counts, so a legacy pack reaches no picker, search or demo; `APPLIANCE_LANGUAGE=sl` fails at startup saying so. See `data/languages/legacy/README.md` to bring one back. Every rule that depends on the spoken language lives in its pack, served by `app/core/language` (`get_language_pack()`); see `docs/core/language.md`.

- **A batch has a language.** It is ingested in the language picked for it (the Ingest view's "Language of these files", the CLI's prompt). A wrong pick for a recording fails the Whisper language check (`LanguageMismatchError`) rather than being forced into it. The source is then un-stamped, so a retry with the right language works.
- **One index holds every language.** Each chunk is keyword-indexed with its own stemmer (`vector_chunks.fts_config`, migration 0004). The sparse leg builds one tsquery per configuration and matches each chunk against its own; the dense leg (BGE-M3) is what finds evidence across languages.
- **Answers are written in the active language**, `settings.APPLIANCE_LANGUAGE`. It is switched between jobs with `IzvoriaBootstrapper.switch_language()`, which rebuilds the engine (seconds, no model load), and remembered across runs (`onyx_data/<ENV>/active_language`). There is **no per-call language parameter**: one engine job runs at a time, so every `get_language_pack()` / `settings.*` call site simply follows the switch. A cache over pack-dependent results must key on the language.
- **The hosted API overrides it per request**, not per call: `language_scope(code)` (`app/core/language/service/language_api.py`) sets a ContextVar that `active_language()` and `get_language_pack()` honour on that thread only, so concurrent users each get their own answer language without touching settings. Read the answer language through `active_language()`, never `settings.APPLIANCE_LANGUAGE`, on the live path; hand work to another thread with `submit_in_context` so the override travels with it. The appliance never sets one.
- **Nothing is translated.** Transcript, index and excerpts stay in the spoken language, because a translated index would put model-written text under every citation. An English answer over Serbian evidence quotes the Serbian excerpt verbatim.

- **Never hard-code language again.** An English word list, an `[a-z]` class, a refusal sentence, a Whisper language code or a stemmer name in new code is a bug on a Serbian appliance. Add a field to the pack instead (`LanguagePack` validates it at startup), and give `en.toml` the value the code used to hard-code, so English doesn't move.
- **Prompts stay English.** Wrap a prompt whose output is stored or shown in `pack.localize_prompt()`; it's a no-op for English. Don't write per-language prompt copies.
- **A pack's `[models]` table overrides Settings.** Serbian swaps Llama 3.2 3B and Qwen2.5-3B for Gemma 4 E4B. An explicit env value always wins.
- **The desktop app's own text is a separate "display language"** (`frontend/izvoria_desktop/locales/<code>.toml`, switched in the app, independent of the answer language). A new served pack needs a display catalog too; `frontend/tests/utils/test_i18n_catalogs_unit.py` fails until it has one. See `frontend/README.md`.
- **Unit tests switch language with the `appliance_language` fixture** (`tests/conftest.py`), which changes it for every module at once; `language_pack(code)` loads a shipped pack.



- **Language / runtime:** Python, no web framework and no server anywhere — `app/main.py` is a CLI entrypoint
  (its own numbered menu, driving `IzvoriaEngine`), and `frontend/main.py` is a PySide6 (Qt6) desktop app that drives the same
  `IzvoriaEngine` **in-process** on a background thread. See `docs/frontend.md` and `frontend/README.md`.
- **Storage:** PostgreSQL + `pgvector`, a **single database for both relational and vector data** (jobs, transcripts, and the `vector_chunks` table with both an `embedding` column and an auto-generated `fts_document` tsvector column live side by side). Run via Docker: `docker-compose.yaml` defines `db_dev` (port 5432, `pgvector/pgvector:pg15`) and `db_test` (port 5433), both bootstrapped from `scripts/init.sql`. **There is no application Dockerfile** — only the databases are containerized; the app itself runs from a local venv.
- **ORM / DB access:** SQLAlchemy + `psycopg2-binary` (sync, not async).
- **Audio pipeline:** PyTorch, NVIDIA NeMo (VAD via MarbleNet, diarization via TitaNet), faster-whisper (domain-adaptation draft pass + main transcription).
- **Vision:** Qwen2-VL-7B via native Hugging Face Transformers + bitsandbytes (4-bit, pre-quantized to disk) — **deliberately not** llama.cpp/GGUF (see gotchas below).
- **Local LLM inference:** `llama-cpp-python` running GGUF checkpoints (Llama 3.2 3B for lightweight NLP/classification tasks — Gemma 4 E4B on Serbian appliances, Qwen 2.5 for correction and retrieval scrubbing, Qwen3.5-9B for QA generation and the Deep Research reasoner), `n_gpu_layers=-1`. Qwen3.5 is a hybrid Gated DeltaNet / attention model: only 8 of its 32 layers keep a KV cache, which is why it runs at a 128K context (`QA_GENERATION_N_CTX`, q8_0 KV cache) on a 12 GB card. Chat calls go through `app/core/model_manager/utils/llama_cpp_chat.py`, which passes `enable_thinking` to the GGUF chat template (`Llama.create_chat_completion` drops template variables).
- **Embeddings:** `sentence-transformers` (BGE-M3), fp16 on CUDA.
- **Reranking:** `sentence-transformers` `CrossEncoder` (bge-reranker-v2-m3, optional — without weights at `RAG_RERANKER_MODEL_PATH` search keeps RRF order).
- **Sentence segmentation:** `wtpsplit` (SaT).
- **Report export:** `fpdf2` (PDF layout), `ziamath` (LaTeX → SVG with its bundled STIX Two Math font), `markdown-it-py` (section bodies); fonts in `data/fonts`. All pure-Python wheels.
- **Documents:** Microsoft MarkItDown (`markitdown[pdf,docx]`, per page, `convert_stream` only; its core EPUB/HTML converters for books), `charset-normalizer` (TXT/Markdown encodings), `striprtf` (RTF, pure Python), `pypdfium2` (page splitting, rendering, image coverage), RapidOCR PP-OCRv5 on onnxruntime CPU for scanned pages. `rapidocr` is installed from **`requirements-nodeps.txt` with `pip install --no-deps`** — it declares `opencv-python`, which overwrites `opencv-python-headless`'s `cv2`. OCR models come from `python -m scripts.download_ocr_models` into `models/rapidocr`; nothing downloads at runtime.
- **Schema migrations:** Alembic, run by `IzvoriaEngine.start()` (`upgrade_to_head`). **A model change needs a revision**: autogenerate it against a fresh scratch database upgraded to head (never `db_test` itself, whose tests drop foreign keys; commands in `docs/core/database.md`), then read it before committing (a `Computed` stemmer must stay `settings.FTS_LANGUAGE_CONFIG`). Never add an `ALTER` to `data/migrations/pre_alembic.py`: it is frozen history for databases from before migrations. Forward-only; see `docs/core/database.md`.
- **Config:** `pydantic-settings`, environment selected by `ENV` (`development`/`test`/`production`) loading `.env` / `.env.test` / `.env.prod` respectively.

## Testing: unit vs integration

- **`tests/` (unit)** — mirrors `app/`'s full internal layering per feature (`data/`, `service/`, `utils/`, `domain/` subfolders match exactly). Fully mocked with `unittest.mock` (`patch`, `MagicMock`) — no real DB, GPU, filesystem, or network. One `TestXxx` class per module under test, methods named `test_<behavior>`, assertions pin down exact call arguments (not just "was called"). Error paths are tested with `pytest.raises(<TypedException>)`. `utils/error_mapper.py` is almost always tested with `@pytest.mark.parametrize` tables.
  Run: `pytest tests`
- **`integration_tests/` (integration)** — flat, one or two files per feature (no internal layering split), plus a root `conftest.py`, plus a `resources/` folder of real fixture media (audio/video/images/JSON transcripts). Uses a **real** Dockerized Postgres (`db_test`, port 5433): a session-scoped `autouse` fixture waits for Docker to be reachable, drops/recreates the schema, re-enables the `vector` extension, and builds it through the migrations (`upgrade_to_head`), exactly as the appliance does; a function-scoped `db_manager` fixture wraps each test in a real transaction + SAVEPOINT that's rolled back afterward for isolation. Real models/GPU are used where available; tests that need hardware or weights not present on the current machine call `pytest.skip(...)` with a descriptive reason rather than failing. Marked with `@pytest.mark.integration` (registered in `pytest.ini`).
  Run: `docker compose up -d db_test`, then `pytest integration_tests -m integration`
- **`frontend/tests/` (desktop unit)** — mirrors `frontend/izvoria_desktop/`, fully mocked, run headless under
  `QT_QPA_PLATFORM=offscreen`. Deliberately has **no `__init__.py` files**: a package named `tests` there would
  shadow the root `tests` package and break collection of the whole existing suite, so filenames carry a `_unit`
  suffix to stay globally unique.
  Run: `QT_QPA_PLATFORM=offscreen pytest frontend/tests`
- **Measurements (not tests):** `scripts/eval/` holds GPU evaluation scripts run by hand. `rag_eval.py` scores retrieval/answers on the dev DB; `language_benchmark` downloads real speech per language (FLEURS, ParlaSpeech-RS, YouTube lectures from `sources.toml`), ingests it into its own `onyx_bench_<code>` database and reports WER, the language guard, throughput and retrieval/answer quality: `venv/bin/python -m scripts.eval.language_benchmark all --language sr en` (needs `requirements-dev.txt`; results under `onyx_data/benchmarks/`). `cross_language` asks every benchmark question in every served language over one database holding all their material, and compares search, chat and reports against asking in the material's own language: `venv/bin/python -m scripts.eval.cross_language all` (results in `onyx_data/benchmarks/cross/results/report.md`). Both measure served languages only.
- **Both:** bare `pytest` runs everything (`pytest.ini`'s `testpaths = tests integration_tests frontend/tests`).
- No CI is configured yet — these commands must be run manually.
- When adding a feature: write unit tests immediately (mirrored directory, mocked). Add an integration test if the feature touches the DB or loads a real model, and make it self-skip gracefully when the resource isn't available rather than failing hard.

## Known gotchas

- **`sys.modules["torchcodec"] = None` hack** in `app/core/model_manager/utils/torchcodec_guard.py` (`block_torchcodec_import()`, used by both embedders and the reranker): scoped to work around a torchvision/torchcodec crash when loading the sentence-transformers embedder, restored in `finally`. `integration_tests/core/model_manager/test_torchcodec_environment_integration.py` proves this can still leak across features within one long-lived process (load the RAG embedder, then later call `torchaudio.load()` for VAD in the same process → `ImportError: TorchCodec is required...`). This is directly relevant to anything long-running that mixes retrieval and ingestion in one process — the RAG agent being built next is exactly that shape. Don't assume this hack is fully process-safe.
- **Qwen-VL must stay on native HF Transformers, not llama.cpp/GGUF** — llama.cpp's `mtmd` vision encoder has a confirmed, unresolved upstream SIGSEGV in the Qwen-VL vision graph allocator. See `app/features/visual_analysis/data/vlm_adapter.py` and `integration_tests/features/visual_analysis/test_vlm_multimodal_diagnostics.py` for the documented regression evidence. Don't "simplify" the vision adapter onto llama.cpp for consistency with the other LLM adapters.
- **Every chat turn re-reads the whole conversation.** The answer model now stays warm between turns (unless the scrubber had to be loaded and evicted it), but llama.cpp's context is not reused, so it still prefills the full history each time (tens of seconds at 50K+ tokens on a 3060). Messages are built append-only so a future KV-state cache (`save_state`/`load_state`, or a dedicated LLM GPU) can reuse the prefix; hybrid models like Qwen3.5 can only reuse state when the new prompt strictly extends the old one.
- **Report mode's model-swap schedule is load-bearing, and a test enforces it.** `ReportAuthoringPhase` is deliberately ONE `execute_report()` covering outline optimisation, every section write and the summary, because each `execute` resolves a preload and unloads in its own `finally` — splitting it in two would mean two loads of the 5.7 GB GGUF instead of one. Likewise `RetrievalAPI.search_batch` acquires the embedder once for a whole fan-out. A full run costs ~6 model loads (2 heavy) on a single-slot pool, and fewer with models kept warm (scoping's load carries into writing); a naive per-section arrangement of the same work costs ~40 (16 heavy). `integration_tests/orchestration/test_deep_research_report_pipeline_integration.py` counts the loads, so a "simplification" here fails loudly rather than silently costing minutes.
- **An unresolved preload can wedge the process, silently.** `Phase.preload_model()` stores a future in `self._preload_future`. If anything returns or raises between firing a preload and resolving it, the next call overwrites that future and the old one becomes **unreachable** — the background worker still loads the model, `discard_preload` can never be called on it, nothing releases it, and the next `acquire_model(..., wait_for_clear=True)` parks forever with no exception and no exit but a restart. `discard_preload` cannot rescue it: `future.cancel()` fails once the task is running, and its done-callback only fires after the load completes, which needs the VRAM it is waiting on. Straight-line pipelines resolve every preload exactly once so this never fired; **any loop must self-guard** (the four report-path phases call `discard_preload()` at the top of `preload_model()`) and discard per iteration, not only in the run's `finally`.
- **`QComboBox.currentData()` does not give you back your enum.** userData is stored as a QVariant, and a `str`-derived `Enum` comes back out as a **plain `str`**. Every gateway branch compares with `is`, so this silently made Reasoned Answer run single-pass chat, Verified search run standard search, and Audio ingest run the video pipeline — all three shipped that way. Each view now rebuilds the enum from `currentData()` at the boundary; keep doing that rather than loosening the `is` comparisons.
- **A file keeps the language it was first ingested in.** Its transcript, glossary, corrections and contextualisation are cached per source, so re-ingesting it with another language selected is refused (`SourceLanguageConflict`) rather than re-indexing the old language's text under the new stemmer. Only a failed language check un-stamps a source (`TranscribePhase`). **Documents and images have no language check**, so a wrong pick sticks until the index is reset.
- **A report is written in one language.** `research_reports.language` is recorded at scoping. The renderer uses that pack, not the active one, and the desktop's resume switches to it first.
- **Tables don't come from MarkItDown.** It reads a borderless table column by column, separating every value from its row. A text-layer page with a table is re-read by `PdfplumberLayoutExtractor` (ruled tables via pdfplumber's line finder, borderless ones via shared column gutters in `document_conversion/utils/layout.py`); scans use the same layout code on OCR word boxes. Don't "simplify" back to MarkItDown's page text, and don't turn on pdfplumber's text table strategy — it cuts prose into cells.
- **Documents: pages are split before MarkItDown sees them, and OCR's missing lines are counted.** MarkItDown joins a PDF's pages and drops empty ones, so a whole-PDF conversion loses page numbers and scanned pages. RapidOCR silently drops every line it recognised as empty, so the adapter runs detection separately and marks a page `ocr_incomplete` when lines went missing; such pages, and scanned pages with no OCR, are listed in the ingestion report. A page is only OCR'd when it has next to no text layer *and* an image covers it — a letters-only rule replaced a sparse born-digital table page with a worse OCR reading.
- **A document chunk's `start_sec`/`end_sec` are 0.0.** Check `anchor_kind` before treating them as times, order and find neighbours by `position`, and print locations through `app/core/anchors` (`format_location`). See `docs/core/anchors.md`.
- **An image's excerpt is machine-written; the OCR check is what keeps invented text out.** Text the VLM reads is indexed only if OCR read it too, and the excerpt and the answer prompts label it a machine description. Don't let VLM text into `raw_text` unchecked, and don't route still images through `ground_observation`: it drops any image without text or marks, which is every ordinary photo. Serbian images are unverified (no OCR) and say so.
- **A LINE anchor's lines live in `page_start`/`page_end`.** Check `anchor_kind` before reading those as pages. The line numbers are the file's own only because TXT/Markdown bypass MarkItDown (it collapses blank-line runs) and `normalize_extracted_text` (same); don't route them back through either, or every cited line shifts.
- **Serbian has no OCR.** No RapidOCR recognition model covers both Serbian scripts (the Cyrillic one lacks č ć đ š ž); `sr.toml` names no `documents.ocr_rec_model`, so scanned pages on a Serbian appliance are reported as unreadable, not indexed. Born-digital Serbian documents work.
- **Ingestion and live inference are currently mutually exclusive** on the appliance — `IzvoriaEngine`'s state lock blocks `search_*`/`chat` while a batch ingestion job holds `INGESTING`. This is a single-GPU-era simplification, not a permanent design decision. The hosted API lifts it differently: `ENGINE_CONCURRENT_LIVE` engines refuse ingestion outright, and a separate worker process ingests one queued batch at a time on the card's other half (`web_deploy/ingest_worker`).
- **On the web version a recording's files are not what ingestion read.** With the hosted storage settings (`docs/web_deploy.md`, "Storage") a chunk has no clip (a citation is cut from the recording on demand), the WAV is gone once a source is indexed, and the original may be a 720p H.264/AAC copy (`app/features/media_compaction`, run last by `StorageCompactionPhase`). Anything that re-reads a source after indexing must cope: re-extract the audio rather than trust an `audio_extractions` row (`AudioExtractorAPI` checks the file), and never assume the stored original is the uploaded bytes (`content_hash` is the upload's). The appliance's defaults keep everything.
- **On the web version the GPU box holds no data.** The databases, vaults and uploads are on the Hetzner VPS (`docs/web_deploy.md`, "Where data lives"). The box reaches Postgres through its tunnel (`box_tunnel.sh`), and the VPS sends an ingestion job's files into the box's scratch and takes its vault back at the same absolute path, because `files.file_path` is absolute. Nothing on the box's live path may read or write a vault file: a new feature that does must go through the gateway (as cited sources do, via `/api/sources/{chunk}/locate`) or through staging, which the **VPS** drives (`gateway/staging_server.py`): the box has no key to the VPS's files. **The box has no database password either**: its processes ask the gateway for the current one per new connection (`web_deploy/common/box_credentials.py`, a `do_connect` hook in `app/core/database/data/credentials.py`), its role `izvoria_box` logs in only while the gateway has it started, and the password changes at every start (`izvoria-box-access`). A new box-side process must call `install_from_env()` before it connects; a new raw `psycopg2.connect` must take `current_password()`. A report keeps no Markdown copy there (`REPORT_FILES_ENABLED=false`). With `PREPARE_VIDEOS` the VPS makes each video's 720p copy before the box sees it (`web_deploy/gateway/prepare.py`): a source's `content_hash` and name then come from the upload record beside the copy (`app/features/storage/utils/upload_record.py`), not from the file ingested; keep `ffmpeg_args.py` and `upload_record.py` standard-library only, because the gateway and the firm-side uploader (`web_deploy/uploader`, which makes the copy on the firm's own computer) import them. Uploads are resumable and parallel (`web_deploy/common/chunked.py`): pieces written at their offset, a marker per piece.
- **RULE: rent only data-centre GPU boxes on Vast ("Secure Cloud" / verified datacenter hosts, in the EU). Never a community or home host, whatever the price.** Whoever has root on the host machine can read everything on the box, and nothing in the code can prevent that: the whole `app/` source (it has to be shipped to run), and while the box runs, the firms' material being processed in RAM/VRAM and this start's database password in process memory, which opens every firm's database until the box is stopped (`docs/web_deploy.md`, "Where data lives"). The hardening only makes this a deliberate attack instead of a `cat`; it cannot make an untrustworthy host safe. A data-centre partner is an accountable, certified business; a home host is anonymous. Also keep one long-lived instance and stop/start it rather than renting a new host each time, so as few operators as possible ever handle client data. The clean end state is a GPU at a provider under contract (e.g. Hetzner), not Vast.
- **The hosted llama-server is patched** (`web_deploy/provision/llama_patches/`, applied by `build_llama_server.sh` to the pinned release). While answers are being written, prompts longer than `ONYX_SHORT_PROMPT_TOKENS` wait, so one long report section can't slow every chat to a crawl. Upstream llama-server reads prompts in slot order and in full batches. Moving `LLAMA_CPP_REF` means re-applying the patch and re-running the spike's stress stage (`docs/web_deploy.md`, "llama-server patch").
- **Live phases keep their preload per thread** (`_preload_future = PreloadSlot()`, `app/orchestration/utils/preload_slot.py`). A Phase object is shared by every request; a new live phase must declare the same class attribute, or concurrent requests resolve each other's preloads.

## Where things stand / what's next

Ingestion (media → transcript → RAG index, including a visual-analysis branch) and retrieval (hybrid RAG search → cross-encoder reranking → verified/hallucination-scrubbed search → cited QA generation via a local Qwen3.5-9B model, which reads only verbatim speaker-labelled transcript text) are both built and wired into `IzvoriaEngine`. See `CHANGELOG.md` for the feature-by-feature history.

**Documents, books and texts** (`ingest_documents()`, `BatchDocumentPipeline`): PDF and DOCX are converted page by page (`document_conversion`, OCR for scans on English appliances); TXT, Markdown, EPUB, HTML and RTF take the same pipeline as further `DocumentKind`s (`DOCUMENT_KINDS` is the one suffix list). Everything is cut along its own clauses, chapters and headings (`document_structuring`), situated by the contextual SLM (`ContextualizerAPI.execute_document`) and indexed beside transcripts. Every chunk is anchored by page (PDF), line (TXT/Markdown) or section (DOCX/EPUB/HTML/RTF) instead of time, so a citation reads `[Doc 3] (p. 7 · Article 7 Termination)` or `[Doc 5] (lines 120–164 · CHAPTER IV.)` in chat, reasoned answers, reports, the CLI and the desktop app. Not yet: XLSX/PPTX/email, document classification and cards, typed fact extraction, Serbian OCR.

**Images** (`ingest_images()`, `BatchImagePipeline`): a standalone image is described by Qwen2-VL's still-image mode, its text checked against RapidOCR, and indexed as one `AnchorKind.IMAGE` chunk cited `[Doc 4] (image)` (`app/features/image_description`, `docs/features/image_description.md`). No transcript stage, no contextual SLM: one VLM load per batch, then the embedder.

**Source profiles** (`app/features/source_profile`, `docs/features/source_profile.md`): every source has a title and topic, written by the contextual SLM at ingestion. Evidence headers read `[Doc 3] <title> (<location>)`, every chunk's `text_payload` starts with `[Source: title — topic]` (never `raw_text`), and a chat or reasoned question that names one source ("in lecture 4") is answered from that source alone (`SourceScopePhase`: lexical shortlist, then the answer model picks). Two things to know: **never put example titles in the profile prompt** (the 3B model copied one onto 25 lectures), and the number guard in `utils/grounding.py` is what keeps a title's lecture/unit number equal to the file name's. Sources ingested before profiles: `python -m scripts.backfill_source_profiles`.

**Four query-time modes, all sharing one citation scheme:**

1. **`chat(query, session_id)`** — single-pass retrieve → scrub → generate, multi-turn. `session_turns` stores each turn with the evidence it showed first, and `[Doc N]` numbers are conversation-wide (`first_doc_number` per turn), so a follow-up can cite an earlier turn's excerpt.
2. **`chat_reasoned(session_id, query)`** — the Reasoner loop (`LiveReasoningPipeline`): multiple retrieval passes judged by a Qwen3.5-9B reasoner, then draft + self-critique. Still ends in one chat answer. This was called "Deep Research" until the report mode took the name.
3. **`propose_research_plan()` → `execute_research_report()`** — Deep Research Report mode (`app/features/deep_research_report/`, `DeepResearchReportPipeline`). A topic in, a multi-page cited Markdown report out, via a WebWeaver-style planner/writer split: sweep the corpus into a numbered evidence bank, assign it to an outline, then write **section by section**, each section seeing only its own evidence. Two calls because the run takes tens of minutes and stops for outline approval first. Holds the GPU exclusively (`EngineState.RESEARCHING`).
4. **`execute_iterative_research_report()`** — Exhaustive mode. Same pipeline, but gathering repeats while sections come back unsupported, up to `REPORT_MAX_GATHER_ROUNDS`. **Code decides *when* to loop** (a section got no evidence; a round added no new chunks); the model only decides *what to ask next*, re-wording a failed query with vocabulary now visible in the evidence bank. Without it, "not covered" conflates "the corpus lacks this" with "the sub-question was worded badly".

**When working on report mode, the things to keep in mind:**

- **`[Doc N]` is assigned once, report-wide**, in reading order, before any section is written — that is what makes a number mean the same thing across sections, the summary, the references table and a resumed run. Per-section citations are then validated against *that section's* allowed numbers.
- **Absence is a finding.** A section the corpus cannot support becomes `SKIPPED_NO_EVIDENCE` and is listed under "Not covered by the available material"; a report states `Coverage: swept N of M indexed sources` rather than implying it read everything. Never let it ship uncited prose instead.
- **One model acquisition per round, and the last round also writes.** `ReportAuthoringPhase.execute_report` takes `stop_on_gaps: bool` — a flag, deliberately not a callback. A callback invoked while the phase holds the model, whose purpose is to decide "go gather more", would hand the next reader the exact footgun the design avoids: re-gathering from inside the residency parks forever on `wait_for_clear`. A one-round exhaustive run therefore costs exactly what a deep run costs.
- **A gathering round must have an unasked query, or it is not entered.** The run keeps a `QueryAttempt` per search (text, round, chunks it added that weren't already banked). The model sees it in the outline prompt so it can re-word rather than paraphrase, and `ReportAuthoringAPI` filters follow-ups against it — the fallback follow-up is derived from a section's title and brief, which don't change between rounds, so without the filter an uncovered section re-issues the identical query until the budget runs out, at three model loads a round. No follow-ups is how the API says "stop". The history is passed only to a pass that can act on it, so deep mode's prompt is unchanged.
- **`research_report_evidence.chunk_id` is intentionally not a foreign key** — re-ingesting a file cascades its chunks away, and a signed-off report must still render its citations from the denormalised provenance.

**Where the desktop app is.** Four views — Chat, Search, Ingest, Report. The Report view (`frontend/izvoria_desktop/ui/views/report_view.py`) does the whole loop: topic + mode, an editable outline approval step, a determinate progress bar, a working Stop, the rendered report with **genuinely clickable `[Doc N]` citations**, and Save as Markdown. Three things about it are worth knowing before changing it:

- **Its citations are the app's only real click-to-verify on prose.** The chat view's chips are `<span>`s and do nothing when clicked — you verify a chat claim through the evidence card beneath it. The report uses `QTextBrowser` + `setOpenLinks(False)` + `anchorClicked` against the `izvoria://doc/N` scheme `markdown_renderer` emits in link mode.
- **Cancel bypasses `EngineBridge`'s worker queue**, the first deliberate exception to "everything through the worker". The worker is busy running the report being stopped, so a queued cancel would arrive exactly when it is useless. Safe only because `cancel_research_report` just sets a `threading.Event`.
- **History reads bypass it too**, on a second thread (`service/history_reader.py`): an ingestion or report holds the worker for hours. Only database-only gateway methods may run there (`HISTORY_CALLS`). History lives in the appliance database (`session_turns`, `search_history`, `research_reports`), shared by every language; see `docs/features/search_history.md`. Reads are refused while the engine is rebuilt in another language, because the database pool is disposed during the switch.

**Hosted, multi-firm web version (`web_deploy/`, `docs/web_deploy.md`).** What demos are shown on and users use: a React/Vite web app; an always-on Hetzner gateway (one address; sign-in is two steps, the firm's sign-in name and shared password, then the person's own account; firm administrators manage their firm's accounts; the owner's console is the firm `admin`; users, sessions and the public request/help pages' submissions in SQLite, emailed by SMTP; Vast start/stop and idle stop; **and every firm's data**: Postgres with each firm's database and the ingestion queue, the vaults and uploads under `/workspace/tenants`, uploads received and cited sources served by the gateway itself, backups); and on the GPU box, which keeps no client data at rest and reaches the data through an SSH tunnel it opens to the VPS, one API process serving every firm (one `IzvoriaEngine` per firm with its own database `onyx_firm_<slug>` and vault, all sharing one `ModelKit`: BGE-M3 and the reranker pinned, the four Qwen roles in `llama-server`'s parallel slots), plus an ingestion wait list run one child process per job. The answer language is picked per question; history (`session_turns`, `search_history`, `research_reports`) carries `owner_id` so each user sees their own. `engine_host.py` is the only module there that imports `app.*`. For personal testing on the 12 GB dev card it also runs locally (`web_deploy/local/run_local.py`: `BOX_MODE=local`, plain HTTP on the LAN, `GPU_SHARING=exclusive`): there the live models hand the whole GPU to ingestion while its queue has work (`/internal/gpu/pause|resume`, `LiveGate`), and every piece of model work in the API must run inside `host.live()` or a pause can't wait for it. Its Ingest page also takes whole folders and, for video, YouTube links and playlists, downloaded by the ingestion worker before it takes the GPU (`web_deploy/common/youtube.py`, `ingest_worker/fetch_links.py`). A rented box's data-centre IP needs a spare YouTube account's cookies (`gateway/youtube_cookies.py`, staged for YouTube jobs only and deleted after the download). This is the web version's only internet access; the appliance has none. A firm's own glossary per language (owner console or `admin_cli set-glossary`; `web_deploy/gateway/glossaries.py`) is stored beside its data on the VPS, staged with each ingestion job and handed to the child as `GLOSSARY_PATH`/`APPLIANCE_INDUSTRY`; without one, the shared general glossary. Its React app copies the desktop app's look (`theme.py`'s palette as CSS tokens, the ink sidebar, three panes); keep the two in step. Same rules as `deploy/`: own venvs, tests with `web_deploy/.venv/bin/pytest web_deploy/tests`. **Before relying on it, run the M0 spike in `docs/web_deploy.md`** (Qwen3.5's hybrid layers under `llama-server --parallel --kv-unified`).

**Hosted demo (`deploy/`, `docs/deploy.md`).** One tester uses the real desktop app from a browser: an always-on gateway VPS (Starlette, Caddy TLS) starts a stopped Vast.ai RTX 3090 through Vast's API, proxies noVNC to it, and stops it again when nobody's connected and the box is idle. An agent on the box launches `frontend/main.py --autostart` with `POSTGRES_DB=onyx` (one database for every language) and `APPLIANCE_LANGUAGE` set to the language the tester picked to start in. A running app is never relaunched for another language: it switches in-app. A cited source opens in the tester's own browser, not on the box: the agent launches the app with `ONYX_SOURCE_OFFER_URL`/`ONYX_SOURCE_OFFER_TOKEN`, `system_open` posts the citation to the agent, and the gateway's `/appliance` page plays or shows it beside the desktop ("Sources in your browser" in `docs/deploy.md`). Without those variables, i.e. on-premise, sources open locally as always. `deploy/` is ops tooling: outside the feature-first layout, own venvs (never add its dependencies to `requirements.txt`), tests in `deploy/tests` run with `deploy/.venv/bin/pytest`. It is not the product's security model — rented hardware, not the client's premises.

**Report titles and PDF export.** A report has a `title` (migration 0006), proposed by the scoping model, editable at outline approval, renamable after (`rename_research_report`); `topic` stays the request, word for word, and is what every prompt is given. Show reports by `display_title` (title, or the request for one from before titles). PDF export is its own feature, `app/features/report_export` (`ReportExportAPI.pdf(report)`): laid out from the stored report (the same content as its Markdown, never from a model) with **fpdf2**, formulas typeset by **ziamath**, fonts bundled in `data/fonts` (Source Serif 4, Inter; OFL). All pure Python, chosen over `QTextDocument`, which gave no running header, bookmarks, inline formulas or usable tables. Three things to know:

- **`math_text` is the one rule for what is a formula.** The writer emits LaTeX unprompted, and prose quotes prices: `$…$` counts only under pandoc's rule, so "$6.40 … $3.00" stays money. The PDF and the web Report page (KaTeX, via the API's `display_math`) both use it; the Markdown download keeps the LaTeX as written.
- **Lines are broken by `line_layout`, not fpdf2**, because a sentence holds formulas and `[Doc N]` tags, which fpdf2's text flow can't put inside a line. Tested as pure arithmetic.
- **Page totals are stamped after layout** (`_Pdf.stamp_footers`): fpdf2's `{nb}` alias can't be substituted inside text set in an embedded Unicode font.

**What's next: DOCX export**, as a second `IReportDocumentWriter` beside the PDF one, via `python-docx` (pure Python). Do not reach for `reportlab`, `weasyprint` or `pandoc`: native deps or a binary, on a box that ships without a package manager. The desktop app doesn't offer PDF yet; `ReportExportAPI` is ready for it.
