# **Onyx AI Appliance 💎**

**Onyx** is an enterprise-grade, fully on-premise AI Appliance engineered specifically for Law Firms and Hospitals.  
Designed with absolute privacy in mind, Onyx provides a powerful audio intelligence and processing pipeline that operates securely on local hardware. No data ever leaves the premise, and organizations benefit from flat-rate, unlimited usage.  
⚠️ **Development Status:** Onyx is currently in active development. **This README reflects only the features currently implemented in the codebase.**

## **📍 Current Status**

The ingestion pipeline (transcription, diarization, visual analysis) and the RAG retrieval side (hybrid search, verified/hallucination-scrubbed search, cited QA generation) are both built and integrated into the engine. Current focus: building the conversational agent that sits on top of RAG for multi-turn, tool-using interaction.

## **🏗️ Current Features & Processing Pipeline**

Onyx operates autonomously, transforming raw media into highly accurate, domain-corrected transcripts. Here is a detailed breakdown of the currently implemented pipeline:

### **1\. Media Ingestion & Extraction**

* **What it does:** Securely monitors local directories, ingests raw video/audio files, and prepares them for AI processing.  
* **How it works:** Uses FFmpeg to isolate and extract a normalized, high-fidelity audio track (usually 16kHz WAV) from various media formats. It uses SHA-256 hashing to deduplicate files and prevent redundant processing.

### **2\. Voice Activity Detection (VAD)**

* **What it does:** Identifies exact timestamps where human speech occurs, discarding silence, background noise, or music.  
* **How it works:** Employs the **NVIDIA NeMo MarbleNet** model. This drastically saves compute time for downstream tasks, as the heavy transcription models are only fed audio segments containing actual speech.

### **3\. Discovery & Domain Adaptation (The "Scout")**

* **What it does:** Analyzes the audio to determine its context (Legal, Medical, or General) and generates a list of highly probable technical terms before the main transcription begins.  
* **How it works:** Uses a rapid, low-VRAM model (**Faster-Whisper Tiny**) to generate a rough draft of the audio. This draft is then passed through a text classifier (**DeBERTa v3**) to confirm the industry domain. Finally, it extracts "hotwords" (e.g., specific medications or legal statutes) to feed into the main transcriber.

### **4\. High-Fidelity Transcription**

* **What it does:** Converts the spoken audio into highly accurate, timestamped text.  
* **How it works:** Utilizes **Faster-Whisper Large v3**. By injecting the "hotwords" generated during the Scout phase as an initial prompt, the model is heavily biased toward correctly spelling complex industry terminology, drastically reducing hallucinations.

### **5\. Speaker Diarization**

* **What it does:** Answers the question "Who spoke when?" by clustering audio segments by speaker voice.  
* **How it works:** Uses **NVIDIA NeMo TitaNet** to analyze voice embeddings. It aligns these speaker tags (e.g., Speaker 1, Speaker 2\) with the text timestamps generated by Whisper.

### **6\. Post-Processing & Phonetic Correction**

* **What it does:** Reconstructs fragmented acoustic text into readable sentences and corrects lingering phonetic mistakes.  
* **How it works:** Uses the **SaT (Segment Any Text)** engine to fix grammar and sentence boundaries. Then, it uses a local LLM (**Qwen 2.5 7B Instruct**) cross-referenced against local domain glossaries to correct highly specific terms, maintaining a strict audit trail of any changes made.

### **7\. Visual Analysis Branch**

* **What it does:** For video sources, detects visually significant moments, extracts frames, and describes them in text grounded to the surrounding transcript.  
* **How it works:** **Visual Cue Detection** flags moments worth analyzing, **Frame Extraction** pulls the relevant frames, and a **Qwen2-VL-7B** vision-language model (native Hugging Face Transformers, 4-bit pre-quantized — not GGUF, due to an unresolved llama.cpp crash in the Qwen-VL vision encoder) describes each frame using the transcript as context. **Visual Hallucination Correction** and **Visual Context Synthesis** then clean up and merge the result with the audio-derived transcript.

### **8\. RAG Indexing & Storage**

* **What it does:** Turns the finished, corrected transcript (audio + visual) into a searchable knowledge base.  
* **How it works:** Chunks are embedded with **BGE-M3** (`sentence-transformers`) and stored in PostgreSQL/`pgvector`, alongside an auto-generated full-text search column — a single table backs both dense (vector) and sparse (keyword) retrieval.

### **9\. RAG Retrieval, Verified Search & QA Generation (query time)**

* **What it does:** Answers a user's question strictly from their own ingested data, with citations.  
* **How it works:** A query is embedded and run as a **hybrid search** (pgvector cosine distance + Postgres full-text rank, combined via Reciprocal Rank Fusion) against the indexed chunks. For **Verified Search**, retrieved chunks are then passed through an SLM-based **hallucination scrubber** that drops anything judged irrelevant or unreliable. For a full chat answer, the surviving chunks are handed to a local **Qwen3.5-9B** model (via `llama.cpp`, 128K context) which generates a response and cites the specific source chunks it drew from. Chat is multi-turn: a follow-up is rewritten into a standalone search query, and the model also sees the earlier questions, answers and excerpts of the conversation, whose `[Doc N]` numbers stay the same for the whole conversation.

## **🧠 The Orchestrator (VRAM Management)**

**The Challenge:** Onyx is designed to run locally. Our development environment is strictly constrained to **12GB VRAM** (a single RTX 3060). Target client hardware is **2× RTX 3060 (24GB VRAM total)**, intended to be split so one GPU serves the ingestion pipeline and the other serves the LLM continuously for live chat — that GPU-affinity split does not exist in the code yet, so today everything still shares one VRAM budget on whichever single GPU is present. We cannot load the VAD, Whisper, Diarization, Correction, and RAG models simultaneously without crashing the system.  
**The Solution:** The **Model Orchestrator** (`app/core/model_manager`).  
This core architectural component acts as a traffic controller for GPU memory, linking every feature above together sequentially:

1. **Job Queueing:** The Orchestrator takes a media file and locks it for sequential processing.  
2. **Dynamic Swapping:** It loads MarbleNet (VAD) into VRAM, processes the audio, and **instantly unloads** it.  
3. It then loads Whisper Tiny (Scout) \-\> Unloads \-\> Loads Whisper Large v3 (Transcribe) \-\> Unloads \-\> Loads TitaNet (Diarization) \-\> Unloads, and so on through every remaining stage, including the vision, embedding, scrubbing, and QA-generation models at query time.  
4. **Result:** By enforcing strict lifecycle control and just-in-time loading, the Orchestrator ensures Onyx never exceeds its VRAM budget, maintaining absolute system stability on constrained hardware.

See `CLAUDE.md` for the full architecture (feature folder conventions, how to add a new feature, testing conventions) and `CHANGELOG.md` for build history.

## **🛠️ Setup Instructions**

There are two ways to run Onyx:

- **A. Local appliance / development machine.** Onyx runs on a Linux box with an NVIDIA GPU (≥12 GB VRAM), which is how the product ships.
- **B. Hosted demo.** A tester uses the real desktop app from a browser. An always-on gateway VPS starts a rented Vast.ai GPU on demand. Your own PC doesn't need to be running.

### **A. Local setup (Debian / Ubuntu, NVIDIA GPU)**

#### 1. Prerequisites

- An NVIDIA GPU with ≥12 GB VRAM and the proprietary driver installed (`nvidia-smi` works). `update_nvidia_driver.sh` updates it on Debian.
- `git`, `ffmpeg`, `curl`, and the build tools for Python (`build-essential libssl-dev zlib1g-dev libbz2-dev libreadline-dev libsqlite3-dev libffi-dev liblzma-dev`).

#### 2. Environment (Python, venv, CUDA, databases)

```bash
git clone git@github.com:StefanovicAleksa/onyx_v3.git
cd onyx_v3
./setup_env.sh
```

`setup_env.sh` is idempotent, so it's safe to re-run. It:

1. builds Python 3.11.9 in user space;
2. creates `venv/` and installs `requirements.txt`;
3. installs the CUDA compiler and rebuilds `llama-cpp-python` with GPU support;
4. installs Docker;
5. starts both Postgres + pgvector containers from `docker-compose.yaml`: `db_dev` on port 5432 and `db_test` on port 5433.

Then install the packages that must skip dependency resolution. `rapidocr` declares `opencv-python`, which would overwrite the headless OpenCV that the desktop app needs:

```bash
venv/bin/pip install --no-deps -r requirements-nodeps.txt
```

#### 3. Configuration

```bash
cp .env.example .env
```

Fill in `.env`:

| Key | Value |
|:--|:--|
| `ENV` | `development` (`.env`), `test` (`.env.test`) or `production` (`.env.prod`); `ENV` selects which file is read |
| `POSTGRES_SERVER` / `POSTGRES_PORT` | `localhost` / `5432` |
| `POSTGRES_DB` / `POSTGRES_USER` / `POSTGRES_PASSWORD` | must match `db_dev` in `docker-compose.yaml` |
| `APPLIANCE_LANGUAGE` | optional: `en` or `sr`, the language the app starts in (Slovenian is a legacy language, not served). One database holds every language; the app switches the answer language at runtime and starts in the one it was last switched to unless this is set |
| `APPLIANCE_INDUSTRY` | optional glossary name under `data/glossaries/<language>/` |

`.env.test` holds the same keys for `db_test` (port 5433), and is needed only for integration tests.

#### 4. Models

Every model loads from `models/`. Nothing is downloaded at runtime, and a missing model fails the phase that needs it. Two download scripts exist:

```bash
./models_download.sh                           # Qwen3.5-9B Q4_K_M (chat, reasoning, reports)
venv/bin/python -m scripts.download_ocr_models  # RapidOCR PP-OCRv5 (scanned PDFs)
```

The rest come from an existing Onyx model set, for example `rsync` from the dev machine. For English and Serbian, that is:

| Path under `models/` | Used for |
|:--|:--|
| `vad_multilingual_marblenet.nemo` | voice activity detection |
| `whisper-tiny-en` | English domain scout |
| `faster-whisper-large-v3` | transcription (and the Serbian scout) |
| `titanet_large.nemo` | speaker diarization |
| `fullstop-punctuation-multilingual-base` | punctuation |
| `llama-3.2-3b-instruct-q8_0.gguf` | English classification, context, ASR correction |
| `google_gemma-4-E4B-it-Q4_K_M.gguf` | Serbian replacement for the 3B models |
| `qwen2.5-3b-instruct-q4_k_m.gguf`, `Qwen2.5-7B-Instruct-Q4_K_M.gguf` | phonetic/visual correction, visual cues, retrieval scrubbing |
| `Phi-3.5-mini-instruct`, `flanec-base-cd`, `deberta-v3-base-zeroshot` | NLP, ASR correction, hallucination scrubbing |
| `qwen2-vl-7b-hf-bnb4bit` | frame and image description (Hugging Face Transformers, not GGUF) |
| `bge-m3`, `bge-reranker-v2-m3` | embeddings and reranking |
| `Qwen3.5-9B-Q4_K_M.gguf` | QA generation, reasoner, reports |
| `rapidocr/` | OCR |

That's about 51 GB. To regenerate the list after adding a model, run `grep -rhoE "[\"']models/[^\"']+[\"']" app data | sort -u`.

#### 5. Run it

```bash
docker compose up -d db_dev                            # if it isn't already up

venv/bin/python frontend/main.py                       # desktop app; click "Start appliance"
venv/bin/python frontend/main.py --autostart           # ...or boot it without the click
venv/bin/python frontend/main.py --stub                # UI only: no GPU, no database, canned answers
venv/bin/python -m app.main                            # CLI menu over the same engine
```

The engine applies database migrations itself on start (`OnyxEngine.start()` → Alembic).

#### 6. Tests

```bash
venv/bin/pytest tests                                                   # unit, fully mocked
QT_QPA_PLATFORM=offscreen venv/bin/pytest frontend/tests                # desktop app, headless
docker compose up -d db_test && venv/bin/pytest integration_tests -m integration   # real DB / GPU

python3.11 -m venv deploy/.venv && deploy/.venv/bin/pip install -r deploy/requirements-dev.txt
deploy/.venv/bin/pytest deploy/tests                                    # hosted-demo gateway + agent
```

### **B. Hosted demo (gateway VPS + on-demand Vast.ai GPU)**

This costs about $35–60/month instead of $200+ for a dedicated GPU server. The GPU box is billed only while it's started, plus its disk.

1. **Rent the GPU box.** On Vast.ai, rent one RTX 3090 with ≥120 GB of disk. Use image `nvidia/cuda:12.4.1-cudnn-devel-ubuntu22.04`, ports `-p 8090:8090 -p 6080:6080`, and on-start script `bash /workspace/onyx_v3/deploy/instance/onstart.sh`.
2. **Copy Onyx and the models to it.** From a machine that has the models:
   ```bash
   deploy/instance/sync_to_box.sh root@<ssh-host> <ssh-port>
   ssh -p <ssh-port> root@<ssh-host> bash /workspace/onyx_v3/deploy/instance/provision.sh
   ssh -p <ssh-port> root@<ssh-host> bash /workspace/onyx_v3/deploy/instance/onstart.sh
   ```
   `provision.sh` prints `AGENT_SECRET` and `WEBSOCKIFY_TOKEN`; keep them for step 4.
3. **Load the demo material.** Ingest it one batch per language, with the Ingest view's language set for each (all into the one `onyx` database), then stop the instance.
4. **Set up the gateway.** On a ~$5/mo VPS with your domain's A record pointing at it:
   ```bash
   git clone git@github.com:StefanovicAleksa/onyx_v3.git /opt/onyx_v3
   sudo bash /opt/onyx_v3/deploy/gateway/install.sh demo.example.com
   sudoedit /etc/onyx-gateway.env      # password, AGENT_SECRET, WEBSOCKIFY_TOKEN, VAST_API_KEY, VAST_INSTANCE_ID
   sudo systemctl restart onyx-gateway
   ```
5. **Send the tester the URL and the password.** They sign in, pick Serbian or English, click **Start appliance** (about 1–2 minutes), upload files and open the desktop. The box stops itself after 30 idle minutes, but never mid-ingestion or mid-report.

Once it's set up, your own PC doesn't need to be on. It's only needed to push code updates, or to re-upload the models if the Vast instance is destroyed, so keep a backup of `models/` somewhere else. The full runbook, the costs and the known risks are in [`docs/deploy.md`](docs/deploy.md). A stopped Vast instance can lose its GPU to another renter, and demo data sits on rented hardware, not the client's premises.
